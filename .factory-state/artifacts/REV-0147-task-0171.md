## Findings

### Blocking

- None. No acceptance criterion fails.

### Non-Blocking

- `mcp_server.py` reads `PersonalAccessTokenRepository` and `WorkflowRepository` itself. Decision 7 puts PAT authentication in the API layer, and the service methods take a user id, a workflow id, and a PAT id. No `WorkflowToken` row is constructed. The service does not import `mcp` or FastAPI.
- `AUTH_ACCOUNT_DISABLED` from `AuthService.current` is re-raised on `/mcp` instead of `TRIGGER_TOKEN_INVALID`. Unknown and revoked tokens are `TRIGGER_TOKEN_INVALID`.
- A name that is not in the visible list is CLI `MCP_DISABLED`. The process does not read stdin.
- `GET /api/workflows/{id}/mcp` uses `phase2=True`, so an HTTP 404 is `SERVER_TOO_OLD`. A visible workflow with MCP off returns `enabled: false` and is `MCP_DISABLED`.

## Standards And Architecture Alignment

- Rate-limit key for a PAT is `pat:{id}:{workflow id}`. A workflow token still uses `token:{id}`.
- `call_for` queues with `TriggerService.queue`, so the run owner is the user and the source stays `api`.
- `mcp` is not in `pyproject.toml`. `.github/workflows/cli.yml` installs `mcp>=1.12,<2` and sets `SUPERSTEP_MCP_TEST=1`.
- `mcp --json` returns 2 before any protocol byte.

## Design Alignment

- The bridge speaks Content-Length stdio and forwards `tools/list` and `tools/call` with httpx. A colliding tool name gets `_<first 6 hex of the workflow id>`.
