### Non-Blocking

- `restore_archive` writes `.env`, `compose.yml`, and `secret.key` before the database load. A failed `pg_restore` or `copy_to` leaves those files in place, and the `finally` block still starts the stack. Format, version, and name checks still happen before any write, which is what the acceptance criteria require.
- The scheduled `backup.sh` is a second implementation of the backup. Its free-space check parses `docker system df -v` text. A missed size makes the estimate too small, and a later failed dump still stops the stack. `create_backup` checks free space before any stop, and the tests cover that path.
- `pg_dump -U studio` and `pg_restore` do not set `PGPASSWORD`. They rely on local auth inside the container. `pg_restore` often exits 1 when it only has warnings. The tests use a fake, so neither shows up. The stop/copy/start fallback is implemented and has no test.

## Standards And Architecture Alignment

- DEC-0068 decision 8: one `superstep-backup-<name>-<utc>.tar.gz`, mode `0600`, with `manifest.json` format `1`, the database, `secret.key`, `.env`, and `compose.yml`. SQLite uses `sqlite3.Connection.backup` inside the container. Postgres uses `pg_dump -Fc`. A short disk on the Python path exits before a stop and before a file.
- DEC-0068 decision 6: `restore` asks for the instance name. `--yes` proceeds only when `--name` equals that name. `--yes` alone is refused. There is no confirm field on an HTTP API.
- The secret is a member of the archive. Command output and `--json` carry the archive path and the instance name, not the key. A successful backup sets `instance.json` `secret_backed_up`.
- `--schedule` writes a shell script that does not call `superstep`. Systemd gets a user timer. Without systemd, the same command writes cron. Prune runs after a successful scheduled backup.
- `create_backup` and `restore_archive` are the functions TASK-0153 calls. No new dependency and no API change.
