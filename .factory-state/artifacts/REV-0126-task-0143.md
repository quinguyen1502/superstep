## Findings

### Blocking

- None.

### Fixed During Review

- **A plain iframe would not have worked at all.** DEC-0067 said Safari would only lose the history. In fact, inside a
  frame the cookie is a third-party cookie: Safari drops it, and so does Chrome over plain HTTP. Without it every
  request is a new visitor, and the socket refuses the session as someone else's. Embedded pages now always send the
  token as `X-Chat-Visitor` and `?visitor=`. A plain iframe keeps the token in its own partitioned localStorage, and the
  widget keeps it on the host page. DEC-0067 decision 7 says so.
- **The frame route.** nginx cannot pass the slug to an `auth_request` subrequest without a variable in `proxy_pass`,
  which needs a `resolver`. The route is now `GET /api/public/chat-frame` and reads `X-Original-URI` (or `?path=`). The
  `/{slug}/frame` route from TASK-0140 (#186) is removed. Nothing else used it.
- **The dev server served the widget as an ES module.** Vite's `transformRequest` output has `import` and `export`, so
  it cannot run as a classic script. The dev plugin now builds it with `vite.widget.config.ts`, which gives the same
  IIFE as production.

### Non-Blocking

- **Hard-coded colours in the widget.** The bubble and panel live on another site and cannot use the studio's theme
  tokens. They are inline styles on two prefixed elements (`#superstep-chat-*`), with neutral colours, outside
  `className`, so `lint:ui` does not apply. The chat inside the frame uses the tokens.
- **The host site can read the widget token** (`superstep-chat:<slug>` in its localStorage). The settings hint says so,
  and TASK-0144 documents it. That site was allowed by the builder.
- **BaseHTTPMiddleware is avoided.** `FrameHeaders` only rewrites `http.response.start`, so streaming responses
  (`/mcp`, file downloads) and WebSockets pass through untouched.
- **The studio's own pages are not covered by e2e.** The Vite dev server does not add the deny headers, so the e2e
  test covers the chat page's `frame-ancestors` and a refused host. The deny headers are covered by
  `test_frame_headers.py`, by `frame_check()` run locally against the API serving `dist/` (all-in-one mode), and by
  the CI smoke jobs.
- **Local Network Access.** Chrome refuses requests from a made-up public page to `127.0.0.1`, so the embed spec
  turns that check off. Real host sites and studios are both public addresses.

## Checks

- Layers: the router reads the header, and the service decides `frame-ancestors`. `static.py` stays in the API layer.
- nginx: `$chat_frame`, `$request_uri` and `$host` are not environment variables, so the image's `envsubst` leaves them
  alone, as it already does for `$host`.

## Decision

Approved for QA. The nginx template can only be checked by the CI compose smoke job; QA records the result.
