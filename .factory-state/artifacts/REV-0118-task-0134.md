## Findings

### Blocking

- None.

### Fixed During Review

- **A local variable shadowed the Agent's state key.** The call key was named `key` inside the tool step, which made
  Python treat the outer `key` (the hidden state field) as local, and every Agent run failed. It is `call_key` now;
  the Agent suites caught it.

### Non-Blocking

- **Waiting reuses the person path.** `AwaitChild` is an `Interrupt`, so the runtime, the checkpoint and the resume
  job need no new mechanism. The checkpoint's `wait` keeps the two kinds apart:
  - a person's answer is refused for a run waiting for a child;
  - a child result (a dict) is refused for a run waiting for a person, and can never be text a person typed.
- **The race between the child's end and the parent's wait.** A child can end before its parent records `waiting`. The
  parent checks right after recording (`resume_parent`), and the child checks when it settles. Both may queue a
  resume; the second is dropped by the claim. `test_a_call_starts_one_child_and_a_second_settle_resumes_once` covers
  the repeated settle.
- **One child per call.** The call key is the step's idempotency key (run, step, iteration) plus the model's call id,
  unique in the database. A retried or recovered step finds the same child and queues nothing.
- **Resources and test rules come from the top parent.** A child uses the top run's resource owner (as an inlined
  subgraph does, DEC-0023) and, under a workflow test, its test rules without becoming a test run itself. Recovery
  and resume use the same helpers.
- **Parents waiting for a child** are not shown as pending, and nobody is notified about them. They still expire after
  `STUDIO_WAIT_TTL` like any waiting run, and an expiry cancels the child.
- **Not covered by a dedicated test:** a workflow tool inside a For each loop. The iteration is part of the call key,
  so each iteration gets its own child; the two-calls test covers distinct keys in one step.
