## Findings

### Blocking

- None.

### Fixed During Review

- **Tool names kept capitals from the workflow name** ("Order_desk_…"), seen in the screenshots. They are now lower
  case, like the other sources' default names.
- **An out-of-date e2e assertion.** `agent-node.spec.ts` expected the English validation text in its vi run, which
  TASK-0132 translated. It now expects the vi text. The other specs had no such assertion.

### Non-Blocking

- **Access.** `GET /api/runs/{id}` uses the same rule as the run history (`_readable_run`): the run's owner, or the
  workflow's owner or an admin. Others get `RUN_NOT_FOUND`. In a public chat's full view, a visitor who cannot read
  the child run sees "The called run cannot be shown here" under the step; nothing leaks.
- **Fetch per call.** Each workflow tool call in a trace fetches its child once when shown. A run has at most rounds ×
  8 calls, so this stays small; a cache was not worth it.
- **The chat's labels mode** stays as it was (tool names only). Only the full view nests the child.
- **Field defaults.** `message` in and `answer` out when the child has them, else the first field in and the last out.
  The validator still requires at least one result field, and the card says so.

## Standards And Architecture Alignment

- UI: shadcn/ui (`Select`, `Switch`, `Button`, `TextLink`) and theme tokens only; `lint:ui` passes. Strings in both
  locales with the same keys. `agent.workflow` ("Workflow") is identical in vi, as the glossary keeps "workflow", and
  is on the reviewed allowlist. There are glossary rows for workflow tool, called run and result.
- Backend: the route only calls the service; the history row is one method shared by the list and the detail.
  `tests/test_layers.py` passes.

## Design Alignment

  under the tool row, indented like Agent steps, with the same status icons. Screenshots are in QA-0120.
