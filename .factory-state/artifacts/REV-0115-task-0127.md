## Findings

### Blocking

- None.

### Non-Blocking

- **The answer is kept only while the run waits.** `keep_resume` updates only `status == 'waiting'`. A run that was
  cancelled or expired in the meantime keeps nothing, and `list_resumes` only returns waiting or running runs.
- **The kept answer is used up at the first record.** `save_progress` and `record` both set `resume_job` to NULL.
  So a resume that saved progress before the restart goes through the usual recovery from that checkpoint, not
  through the kept answer. A resume that ends waiting again (a second Human node) also clears it.
- **Recovery handles kept answers first and skips them in the usual loop.** A `running` run with a kept answer goes
  back to `waiting` before the job is queued again, so the worker's claim works as for a fresh answer. The recovery
  limit (`STUDIO_RECOVER_MAX_ATTEMPTS`) still applies.
- **Two answers through MCP `resume_run`.** That path does not close a waiting step, so two quick calls can both queue a
  job; the second overwrites the kept one. This was already possible before the task (two jobs, first answer
  wins, DEC-0043), and recovery queues only the last kept one.
- **Redis is unchanged.** `keep_resume` also writes with Redis, but only the in-memory recovery reads it. With Redis
  the reaper already requeues lost jobs, and the kept job is cleared by the same record calls.
- **`set_status(..., "waiting")` is not fenced.** It runs once at start-up, before the worker loop takes jobs, with
  the single-process in-memory queue, so no other worker can hold the run.
